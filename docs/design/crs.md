# Data in any CRS, and a basemap on a projected map — design

> **Status: Phase 1 (gap 1) IMPLEMENTED** on branch `feature/data-crs`, release pending; Phases 2–3 to do. Tracking issue: `onlymap-js #2`
> (steps 1 and 2 of its §0 sequence). Written 2026-10-06 against core 0.11.9 and
> nika-agent `feat/element-picker` @ `690dbd0`. Versions are assigned at release.

Two gaps, in priority order, and the contract that keeps the standalone library and
nika-agent placing the same file in the same place.

1. **Data in a local grid.** A layer whose coordinates are eastings/northings (SVY21,
   British National Grid, State Plane, UTM) draws in the ocean or is refused. The map
   must accept it, from the file's own CRS metadata or an author's declaration.
2. **A basemap on a projected map.** `<om-map crs="…">` can draw data and relief but no
   street map underneath: MapLibre basemaps and image-tile layers are both refused.

Out of scope here (deferred, §6, in this order): survey-grade datum grids (OSTN15, NTv2),
native tile pyramids (`TileMatrixSet`, carto-substrate Phase 6b), globe, GPU projection.

---

## Decisions (2026-10-06)

| # | Decision |
|---|---|
| D1 | Gaps 1 and 2 are the priority, in that order. Gap 3 (correction grids) waits for a user who needs ~10 cm. |
| D2 | **The core may look an unknown EPSG code up online** (epsg.io PROJJSON — the same lookup the GeoTIFF layer already makes). Offline or blocked, it is a structured error with a fix, never a guess. |
| D3 | **nika-agent keeps converting with GDAL** (§4). Consistency comes from a shared contract and a shared resolver, not from one engine. |
| D4 | **No automatic basemap swap on a projected map.** `basemap=` stays a validation error under `crs=`; its fix shows the `TileLayer` line to write. A silent swap would change the basemap's look (labels baked in and tilted by the projection, blurrier), sometimes its provider, and sometimes into a key watermark (keyless CARTO raster) — and the author should choose a raster provider and its usage terms knowingly. |
| D5 | **Online lookup: on by default, rare, disclosed, switchable.** Bundle generously so it almost never fires — every WGS84 and ETRS89 UTM zone is generated by code, plus the common national grids. README and llms.txt name the request (`https://epsg.io/<code>.json`, from the reader's browser, first load only, cached per session), and the GeoTIFF/Zarr layers' existing undisclosed lookup gets the same sentence. `OmMap.configureCrs({ online: false })` turns it off; a missing code is then an error naming `registerCrs`/`crs-def`. |

## 1. Verified: where the two disagree today

Measured in the code on 2026-10-06, not recalled.

| Data | nika-agent | Core 0.11.9 |
|---|---|---|
| Shapefile | GDAL reads the `.prj` and converts (`convert_to_wgs84_geojson` → `ogr2ogr -t_srs EPSG:4326`) | **ignores the `.prj`** — `@loaders.gl/shapefile` defaults `gis.reproject` to false; a BNG file lands in the ocean, silently |
| GeoParquet, non-CRS84 | converts | refuses (`geoparquet.ts` CRS84 guard: "reproject first, e.g. ogr2ogr") |
| FlatGeobuf | converts | ignores the header CRS (`fgb.geojson.deserialize`) |
| GeoPackage | converts | no reader |
| GeoJSON with a legacy `crs` member | read as lng/lat (not routed to GDAL) | read as lng/lat |
| CSV / Excel easting–northing | lat/lon column detection only (`csvToGeojson.ts`) | whatever `get-position` returns, assumed lng/lat |
| GeoTIFF | `gdal_translate -of COG`, then the core's COGLayer | COGLayer reprojects (deck.gl-geotiff) |

**Four definition resolvers**, which is how the same code could resolve two ways:

1. `src/crs.ts` — a bundled table of 20 codes (BIM/CityJSON placement).
2. `src/projection.ts` — the plane view: bundled + `registerCrs` + `crs-def`.
3. `@developmentseed/proj` `epsgResolver` — epsg.io PROJJSON, inside the GeoTIFF/Zarr layers.
4. nika-agent `omShims.ts` `projectorTo4326` — its own proj4 + epsg.io, for raster overviews.

**The seam nika-agent already uses** (`omShims.ts` header, verified against
`data-layer.ts:535`): `OmMap.registerFormat` puts its GDAL-backed formats for
`.shp/.gpkg/.fgb/.parquet` ahead of the core's built-ins. The manifest keeps
`data="nika-file://<original>"` plus `data-nika-path`; conversion caches
(`~/.nika/cache/map-render/`, freshness-checked) never appear in a manifest; the
standalone export embeds the converted GeoJSON (zip export for large files).

## 2. The shared contract (both repos)

1. **Coordinates enter the map as longitude/latitude.** Conversion happens once, when
   the data loads — never per frame.
2. **The file's own CRS metadata is authoritative**: shapefile `.prj`, GeoParquet
   PROJJSON, FlatGeobuf header, GeoJSON `crs` member, GeoTIFF keys.
3. **`crs="…"` on a layer declares what the source data is in**, and overrides the file.
   This is what `crs` already means on `ZarrLayer` and on a static `<om-frame>`. On
   `<om-map>`, `crs` stays the projection the map is *drawn* in — a different question.
4. **Never guess.** No metadata, no declaration, coordinates outside ±180/±90 → an
   error that names the fix. A declared projected CRS on coordinates that are already
   degrees → a warning ("already longitude/latitude? remove crs").
5. **One resolver** turns a CRS into a definition: bundled → registered (`registerCrs`)
   → `crs-def` → online (D2). Exported from the core; nika-agent calls it.
6. **Whoever converts says so.** A format plugin that returns longitude/latitude reports
   it (§3.4), so the core never converts twice.

## 3. Gap 1 — data in any CRS (core)

### 3.1 One resolver

`resolveProjection` (`projection.ts:184`) becomes the only resolver:

- `crs.ts`'s table folds into the projection registry — one table, one set of tested
  definitions (they are already the same proj4 strings).
- Accepts an EPSG code (`EPSG:27700`, `27700`, `urn:ogc:def:crs:EPSG::27700`), a WKT
  string (a `.prj` body), or a PROJJSON object — proj4 2.20 parses all three natively.
- Online step (D2): `https://epsg.io/<code>.json`, cached per session; the GeoTIFF
  layer's existing cache is reused, not duplicated. `OmMap.configureCrs({ online: false })`
  turns it off for air-gapped hosts. A failure is the structured error
  `crs="EPSG:9999" could not be resolved (offline, or unknown) — register it with
  OmMap.registerCrs("EPSG:9999", "+proj=…") or set crs-def`.
- Exported (`resolveProjection` already is; add `toLngLat(crs)` → a batch converter).

### 3.2 Finding the source CRS, per format

| Format | Source of the CRS | Notes |
|---|---|---|
| Shapefile | `.prj` sidecar (WKT), fetched through the same `dataFetch` as `.dbf` | missing `.prj` + projected-looking coordinates → the §2.4 error |
| GeoParquet | PROJJSON in `geo.columns[g].crs` | the CRS84 guard becomes "convert, or error only if unresolvable" |
| FlatGeobuf | header `crs` (`org`/`code`, or `wkt`) | read before deserialising |
| GeoJSON | legacy `crs` member (`name` → `urn:ogc:def:crs:…`) | RFC 7946 removed it; real files still carry it |
| CSV / Arrow / inline rows | none — `crs=` on the layer | eastings/northings through `get-position="[$x, $y]"` |
| KML / GPX | WGS84 by specification | unchanged |
| GeoTIFF / COG / Zarr | the file / existing `crs` attribute | unchanged; now resolved through §3.1 |

### 3.3 Where conversion runs

The same seam as geometry transforms (`applyTransformStage`): after normalisation,
before accessor resolution, in BOTH front-ends (`parse-manifest.ts`, `descriptorToIR`),
so deck, `anchor="surface"`, the legend, ctx, picking and the vector exporter all see
one geometry. Two cases, mirroring `plane-layers.ts`:

- **Geometry carried as data** (GeoJSON features, shapefile, FlatGeobuf, GeoParquet):
  coordinates are converted once into a new array (the author's array is never
  mutated — it may be the inline memo). Memoised per (data, crs).
- **Geometry read through an accessor** (CSV/Arrow x/y columns): positional accessors
  are wrapped, memoised per (accessor, crs) so deck's update triggers stay stable —
  the `wrapAccessor` precedent exactly.

On a projected map the two compose: source → lng/lat → plane. When the source CRS *is*
the map's CRS (BNG data on a BNG map), skip the round trip and place it directly — exact,
and no datum shift applied and un-applied.

Large datasets convert in a worker (threshold set by measurement in Phase 1, step 6);
the layer reports `loading` until it lands, through the existing data lifecycle.

### 3.4 The format-plugin contract

`DataFormat.parse(res, url)` gains an optional third argument and an optional result
shape, both backward compatible:

```ts
parse(res: Response, url: string, ctx?: { crs?: string }): Promise<LayerData | { data: LayerData; crs: string }>;
```

- `ctx.crs` is the layer's declared `crs`, so a plugin can honour it (nika-agent passes
  it to GDAL as `-s_srs`; without this a `.shp` with no `.prj` could not be fixed by
  declaring its CRS in the app).
- Returning `{ data, crs: "EPSG:4326" }` tells the core the data is already
  longitude/latitude: the layer's `crs` was about the *source* and has been honoured.
  Returning bare `LayerData` means "as the file is" — the core applies §3.2 and the
  declaration.

### 3.5 Authoring surface

- `crs` on `<om-layer>` for every vector/row type (registered universally, like
  `visible-zoom-range`; the raster types keep their own `crs` prop, same meaning).
- `crs-def="+proj=…"` beside it for a CRS nobody has registered (the `<om-map>` precedent).
- Validation: unresolvable code (error, §3.1 text); declared projected CRS on degree
  coordinates (warning); undeclared projected-looking coordinates (error — the silent
  ocean case becomes loud; checked where the rows are in hand, like `classify-*`).
- React/descriptor: `crs`, `crsDef` in `DESCRIPTOR_PROP_MAP`.

## 4. nika-agent — keep converting, align to the contract (D3)

Keeping GDAL is the cleaner split, not a compromise: GDAL reads more formats
(GeoPackage), parses every `.prj` dialect, and on a machine with PROJ's grids applies
datum corrections the browser cannot yet. The registered-format seam means the core's
new built-ins never run on those files in the app, so nothing converts twice.

| Change | Why |
|---|---|
| The GDAL format honours `ctx.crs` as `-s_srs` | a file without metadata is fixed the same way in the app as in a standalone page: by declaring `crs` |
| It returns `{ data, crs: "EPSG:4326" }` | the core must not re-apply the declaration (§3.4) |
| `projectorTo4326` → the core's exported resolver | one resolver (§2.5); drops the duplicate epsg.io path |
| `csvToGeojson`: when the layer declares `crs`, accept x/y (easting/northing) columns and convert through the core's converter — or defer that case to the core's CSV path | easting/northing CSVs work in the app too |
| Skill guidance: `crs=` on a layer means "the data is in"; unnecessary for shp/gpkg/fgb/parquet in the app (GDAL reads the file), needed for CSV and files without metadata | the model writes the same markup a standalone author would |
| Vendored llms.txt / html-data at the release (the usual four homes) | — |

**The one place they can still disagree**, documented rather than hidden: for CRSs with
a datum shift (BNG, NAD27, RD New), GDAL with PROJ's correction grid can differ from the
core's built-in shift by up to a few metres. The same file placed in the app and in a
hand-written page can sit 1–3 m apart. Invisible on a map at city scale; gap 3 (§6)
closes it when someone needs survey accuracy.

## 5. Gap 2 — a raster basemap on a projected map (core)

The warp that draws `HillshadeLayer` on a projected map (`plane-warp.ts`,
`plane-tileset.ts`, measured 0.40 output px for Albers at z3) generalises to any
image-tile layer:

- `TileLayer` with an image template (`{z}/{x}/{y}.png|jpg|webp`) gains the plane path:
  `PlaneTileset2D` picks Mercator tiles from the plane's geography, each tile is
  subdivided and drawn as a warped mesh. *(As built: `warpsInPlane` is per type and
  only a TileLayer's image templates warp, so the validator skips an image TileLayer
  explicitly and still refuses one of `.pbf` tiles.)*
- `MVTLayer`, `TerrainLayer`, `Tile3DLayer` and MapLibre basemaps stay refused (vector
  basemaps in a plane are the GPU trigger in issue #2).
- No automatic swap (D4): `basemap=` on a projected map stays the existing validation
  error, whose fix now shows the `TileLayer` line to write.
- Attribution: **the author's, not the map's.** *(Corrected 2026-10-07; the first draft
  said the badge and sheet credit would collect the tile layer's credit. They do not,
  and should not: the map credits only the basemaps it picks, and tiles an author names
  in a `TileLayer` are the author's to credit — the standing tileset-attribution
  stance.)* The `basemap=` error's fix for a raster preset carries the preset's credit
  as a ready `<om-widget type="attribution" text="…">` line, so moving a preset into a
  layer does not lose it.
- nika-agent / skills: the cartograph rule "`basemap="none"` is REQUIRED on a projected
  map" relaxes to "raster basemaps are fine on a projected map; MapLibre basemaps are
  not" — in both repos' guidance in the same release.

Acceptance: an OSM raster basemap under BNG and under EPSG:5070, deviation measured
against a proj4 reference at tile corners and mid-cells (sub-pixel, as for relief), pan
and zoom at z6–14 without seams. *(The sheet-credit clause is withdrawn with the
attribution correction above.)*

## 6. Deferred, in order

Parked behind gaps 1 and 2. Each says what it is, why it waits, and what would start it.

### 6.1 Correction grids (survey-grade datum accuracy)

**What.** Converting a grid with its own datum (British National Grid, NAD27, RD New)
to longitude/latitude uses a seven-number formula good to a few metres. The national
agencies publish a measured correction grid (OSTN15 for Great Britain, NTv2 `.gsb` files
elsewhere) that brings it to centimetres. `registerGrid(name, bytes)` over proj4js's
`nadgrid` support would let a definition reference one.

**Why it waits.** A few metres is invisible on a map at city scale; it matters for
engineering layout and cadastral work. The grid files are megabytes, so the author would
supply them, not the library.

**Consistency.** The same grid file must give the same answer in nika-agent and in the
browser, so the app passes the grid to the core rather than relying on whatever PROJ
data the user's machine has. Measure a real install's GDAL output against the core's
first.

**Trigger.** Someone needs better than a few metres on a datum-shifted grid.

### 6.2 Native tile pyramids (`TileMatrixSet`)

**What.** A basemap is millions of small images cut on a fixed grid; almost every tile
server cuts them on the Web Mercator grid. A few national agencies also serve a second
set cut on their own grid — Ordnance Survey in British National Grid, swisstopo in LV95.
A `TileMatrixSet` describes such a grid (origin, tile size per zoom, projection; the OGC
WMTS shape). Supporting it would load those tiles exactly as served, with no stretching.
This was carto-substrate Phase 6b.

**Why it waits.** Gap 2 already gives a projected map a basemap by warping ordinary
Mercator tiles, which works for every projection and every provider and measured under a
pixel of error for relief. Native pyramids only save one resampling step, for the
handful of countries that publish them. It is also the literal route to issue #2's
"tiles within 1 px of QGIS" acceptance, if that is ever wanted literally.

**Trigger.** A user asks for a specific agency's tiles by name.

### 6.3 Globe view

**What.** Drawing the Earth as a sphere that spins, as Google Earth does when zoomed far
out — the answer for whole-hemisphere and polar maps (Antarctica), which no flat
projection shows well. Architecture doc Q10.

**Why it waits.** It is a separate feature from local grids. deck.gl and MapLibre both
ship a globe mode, so it is mostly wiring plus a list of layers that cannot draw on a
globe, each a validation error.

**Trigger.** A global or polar map request, independent of this design.

### 6.4 GPU projection

**What.** Today a projected map converts coordinates once, on the CPU, when the data
loads, then draws them. The alternative rewrites deck.gl's core drawing code so the
graphics card converts every point every frame — issue #2's "Layer 2".

**What it would buy, and only it.** Switching a live map's projection instantly without
reloading, and drawing vector (MapLibre-style) street basemaps in any projection at full
speed.

**Why it waits.** It means maintaining our own fork of the deck.gl code every layer and
extension depends on, in two shader languages, on an exact pin that is already costly to
move; deck.gl's own globe took several releases and is still experimental. Nobody has
asked for either thing it buys.

**Trigger.** A real request for live projection switching, or for vector basemaps on a
projected map at scale.

*Picked up 2026-10-12 as a bounded study, not a build: `docs/design/gpu-projection.md`
(issue #49). Live switching turned out not to need the GPU — it ships on the CPU path
first — so the study's question is vector tiles in a plane.*

## 7. Plan

**Phase 1 — gap 1, core.**
1. Fold `crs.ts`'s table into the projection registry; accept WKT/PROJJSON; the online
   step with `configureCrs({ online })`; tests against epsg.io-shaped fixtures (no live
   network in unit tests).
2. Source-CRS discovery: `.prj`, GeoParquet PROJJSON, FlatGeobuf header, GeoJSON `crs`
   member — one fixture per format in a local grid (BNG and SVY21), asserted against
   independent reference coordinates.
3. The conversion stage in both front-ends (data and accessor cases); the same-CRS
   shortcut on a projected map.
4. `crs`/`crs-def` on layers; validation (three entries); IntelliSense; React props.
5. `DataFormat` ctx + result shape; a test plugin that returns `{data, crs}`.
6. Worker threshold by measurement (a 1M-vertex shapefile); e2e: a BNG shapefile and an
   SVY21 CSV on a Mercator map and on a BNG map, overlaying a lng/lat reference layer.
   **Measured 2026-10-06:** proj4 converts 2.6 M vertices/s on the main thread for BNG
   (with its datum shift), 3.9 M/s for SVY21 — a 1M-vertex file in ~0.4 s, once, less
   than parsing it costs. **No worker in Phase 1.** Revisit if someone loads >5M vertices.

**Phase 1 as built (deviations from the plan above):**
- `crs.ts` stays the table module; `projection.ts` is the one resolver over it (the BIM
  helpers keep their own thin converter over the same table). No second table.
- The online step fetches `https://epsg.io/<code>.proj4` (plain proj4 text, the table's
  own format) into its own session cache; the GeoTIFF/Zarr layers keep their library's
  `.json` lookup. Same host, same disclosure; `configureCrs({ online: false })` governs
  only ours — making it govern theirs too is a follow-up.
- The same-CRS shortcut (BNG data on a BNG map, skipping the round trip) is not built: the
  round trip measured sub-millimetre, so it would only save time.
- **Found and fixed:** the core never read a shapefile's `.prj` — loaders.gl asks for a bare
  `.PRJ` when given a custom fetch. The core now fetches the `.prj` itself, like the `.dbf`.
  The same bug loses `.cpg` (DBF text encoding); not fixed here.
- `basemap=` under `crs=` keeps its old error text until Phase 3 builds the raster path its
  new fix will point to (D4).
7. Doc surfaces (README, skill, llms.txt, html-data, architecture, CHANGELOG), issue #2.

**Phase 2 — nika-agent alignment** (after Phase 1 is published): §4's table.

**Phase 3 — gap 2, core.** §5; then the skill rule in both repos.

**Phase 3 as built (2026-10-07):**
- `WarpedBitmapLayer` (a `BitmapLayer` whose `_createMesh` is `buildWarpMesh`) is the
  image TileLayer's sub-layer on a plane; the TileLayer gets `PlaneTileset2D` and
  `minZoom: -Infinity`, memoised per plane so deck sees one `TilesetClass`.
- Measured in `e2e/projected-raster.spec.ts`: synthetic tiles paint discs at known
  places; each disc's centre lands within **0.7 px** of `map.project()` on BNG (z4.4)
  and Albers (z2.8), against 0.45 px for the Mercator control. No uncovered pixels.
  The same image-tile pyramid level is fetched as on Mercator.
- **Found and fixed:** the warp spread a tile's texture rows evenly in latitude; a Web
  Mercator tile's rows are even in Mercator y. That put every interior row south of
  where it belongs — 6.3 px at London on the BNG sheet. The relief warp shares the
  mesh, so projected relief had the same offset since it shipped; the relief suites
  measure texture and seams, never position, so none caught it. `lngLatAt` now
  interpolates Mercator y.
- The `basemap=` error's fix is the preset's own tiles as a `TileLayer` plus its credit
  line; a vector preset gets the generic image-tile line. No swap (D4).
- Still open from §5: the cartograph skill rule in nika-agent (Phase 2's list).
